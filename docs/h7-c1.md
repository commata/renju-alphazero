## 구현 1–3, 5 (2026-10-23)

**`src/hybrid/h7c_targets.py`: target과 표본 규칙(생성기와 label 단계가 같은 함수를 쓴다)**
- TB-V3의 route 분류
  - 증명된 승리: `stage1`(지금 오목), `stage3`(막을 수 없는 사), `own_vcf`, `own_vct`(V8-B), `own_vct2`(E4-v2)
  - tree: `v8_root_visits`에 root 자식의 (수, 방문, 평균값)이 있다.
  - 강제 수: `stage2`(오목 막기), `stage4` / `stage5`(강제 방어). tree가 돌지 않아 방문 분포가 없다.
- 증명된 패배 후보: 그 수에서 root · VCT2 · stage-VCT 검사가 `UNSAFE`(PROVEN_LOSS_VCT1)로 판정한 수
- policy target
  - `proof_one_hot`: 증명된 승리 route. 둔 수에 확률 1, KL 없음
  - `visits`: tree의 방문 분포에서 증명된 패배를 0으로 두고 다시 정규화. KL 적용
  - `none`: 강제 수, 또는 방문이 모두 증명된 패배인 경우. policy loss 없음
  - 원본 방문 수(`[행, 열, 방문, 평균값]`)는 항상 함께 남는다.
- 표본(opening 뒤 처음 4수, T = 1)
  - 증명된 승리는 그 수를 둔다(`proven_win`).
  - tree는 위 분포에서 뽑는다(`sampled`).
  - 그 밖에는 엔진의 수를 두고 기록한다(`no_distribution`).
- 강제 수(`stage2` / `stage4` / `stage5`)의 policy target은 `none`이다(policy 학습에서 뺌, value 라벨은 남음). 사용자 승인으로 확정했다(아래 "승인 보충").

**`scripts/h7c_selfplay.py`: 생성기**
- 엔진: 양쪽 모두 `tb_v3_net.make_tb_v3_net_agent`(동결 TB-V3 / fast5, 후보 모델). 대국마다 색별 agent 하나(E4-v2 cooldown이 agent마다 있다)
- seed
  - 학습 run seed는 8801–8999다. 8800은 처리량 측정 전용이라 생성기가 학습 run에는 거부한다.
  - 대국 seed = `derive_seed(run_seed, 'h7c', cycle, i)`, opening seed = `derive_seed(run_seed, 'h7c-opening', cycle, i)`
  - 충돌 · 예약 seed를 검사한다.
- 대국마다 남기는 것
  - run identity: 엔진 해시, value 장치의 fast5 runtime 해시, 모델 SHA 4개와 그 해시, `frozen_models`, opening · 표본 · target 형식
  - 코드 커밋, opening, 결과(`real_draw`는 판이 다 찬 무승부만)
  - 수마다: route, 엔진의 수 / 둔 수, 표본 사건, 원본 방문, 증명된 패배, policy target, E4 실행 여부
- 이어하기: 끝난 index는 건너뛴다. 다른 run(seed, cycle, 모델, 엔진, runtime, 규칙)의 파일은 거부한다.
- 더러운 tree는 거부한다. 진행 출력은 1분마다(`run_chunks`)다.
- 테스트: 무작위 망(동결 구조)의 실제 후보 agent로 대국을 둔다. 같은 seed면 같은 대국이고, 이어하기 · 거부도 확인한다.

**`scripts/h7c_labels.py`: label 단계 (H6 규칙 재사용)**
- 증명: `build_h6_labels`의 proof task와 같은 예산. 증명 1.0, 결과 0.1이고, 증명이 결과보다 우선한다.
- value 행은 H6 행 형식 그대로다. 그래서 `h6_value_cache` / `h6_value_train`이 바로 읽는다.
- probe
  - probe 국면이 든 대국은 통째로 뺀다(`default_probe_files` + `--probe-files`로 웹 probe 추가).
  - 3수 opening probe만 행 단위 mask다(H6-v2 규칙).
- split: 대국 단위(`split_for`, salt `h7c-v1`, val 5%). 뒤 split의 중복 국면은 mask하고 `check_leakage`를 통과해야 한다.
- 입력 검사: 한 cycle · 한 모델, 학습 run seed만, 잘린 대국 없음, 중복 없음, 수와 수별 기록이 일치
- policy 행(`h7c-policy-row-v1`): target 종류, KL 여부, target, 원본 방문. probe 행 · 뒤 split 중복은 value 행과 같이 mask한다.
- 출력은 `data/`나 `runs/` 아래로만 쓴다.

**`scripts/h7c_throughput.py`: worker 재현성과 처리량 (운영 값)**
- `repro`: run seed 8800, 4국을 worker 1과 12로 두고, 시간 외 모든 기록이 같아야 `REPRO_PASS`다.
- `sweep`: 같은 20국을 worker 6 / 8 / 10 / 12 / 14로 둔다.
  - 기록: 시간당 대국, 수 평균 · p99, GPU 사용률 · 메모리(nvidia-smi), CPU 사용률
  - 선택: 최고의 95% 안에서 가장 적은 worker
- 이 환경에서 무작위 망으로 worker 1 / 2 비교 `REPRO_PASS`를 확인했다(테스트).

**실행 명령 (데스크톱, `feat/h7-c1`)**

```bash
cd ~/renju-h6 && git fetch origin && git checkout feat/h7-c1 && git pull --ff-only && source .venv/bin/activate
```

## 승인 보충 (2026-10-23, 구현 검토 반영)

**seed 이름 공간 (원 승인의 8800–8999를 나눈다)**
- 8800: worker 재현성 · 처리량 측정 전용(`scripts/h7c_throughput.py`). 이 대국은 학습 데이터가 아니다. 생성기는 8800으로 학습 run을 거부하고, label 단계도 거부한다.
- 8801–8999: 학습 run seed. 대국 seed는 `derive_seed(run_seed, 'h7c', cycle, i)` 그대로다.

**강제 수 policy target: `none` (승인)**
- 이유: `stage2`는 상대 오목 후보가 여럿일 때 그중 하나를 고르고, 방어 route는 heuristic tie-break의 영향을 받는다. one-hot으로 배우면 강제 규칙이 아니라 기존 엔진의 임의 tie-break를 외울 수 있다.
- 나중에 "합법 방어가 정확히 하나"임을 증명하는 route가 생기면 그 경우만 one-hot으로 넓힌다.

## 재현성 · 처리량 결과 검토와 Rapfi Pre-RL 기준선 준비 (2026-10-23, `a91f0bd`)

**검증 (`docs/h7c/h7c1_repro.json`, `docs/h7c/h7c1_throughput.json`)**
- 두 기록 모두 생성기 커밋 `048bc04`(깨끗한 tree), run seed 8800, cycle 1, 동결 모델(`frozen_models: true`, model hash `e0d88f75…`), 엔진 `d0ef0da6…`, CUDA runtime `7c727150…`이다.
- repro: worker 1 대 12, 4국, 시간 외 기록 4/4 동일 → `REPRO_PASS`
- sweep: worker 6 / 8 / 10 / 12 / 14 모두 같은 20국(782수) → `SWEEP_PASS`, 규칙대로 `chosen_workers: 6`
- 초안의 표와 수치는 결과 파일과 같다.

**초안에서 고칠 것 1: 처리량 해석.** "worker를 늘릴수록 처리량이 줄었다"는 이 측정에서 나오지 않는다.
- 20국 sweep의 시간은 대부분 고정비용이다.
  - worker 수만큼의 프로세스 시작과 모델 · CUDA 적재
  - 마지막 대국이 끝날 때까지의 꼬리
- 수 평균 × 수 수로 계산한 실제 탐색 시간과 비교하면 다음과 같다.

| worker | 대국당 탐색(초) | 이상적 wall(초) | 측정 wall(초) | 잔여 overhead 추정(초) | 정상상태 낙관 추정(대국/시간) | CPU |
|---:|---:|---:|---:|---:|---:|---:|
| 6 | 22.5 | 75.0 | 140.0 | 65.0 | ≈ 960 | 20.8% |
| 8 | 23.8 | 59.6 | 141.2 | 81.6 | ≈ 1,210 | 22.0% |
| 10 | 26.6 | 53.3 | 143.8 | 90.5 | ≈ 1,350 | 24.2% |
| 12 | 28.2 | 47.1 | 149.5 | 102.4 | ≈ 1,530 | 25.5% |
| 14 | 32.1 | 45.9 | 152.2 | 106.3 | ≈ 1,570 | 27.2% |

- 측정 wall은 140–152초로 거의 같다. 잔여 overhead(측정 wall − 이상적 wall)는 65초에서 106초로 늘었다.
  - 이것은 고정비용 측정이 아니라 잔여 추정치다. worker 시작 · CUDA 적재, 대국 길이 불균형과 꼬리, 프로세스 스케줄링, CPU / GPU 경합이 모두 섞여 있다.
  - "worker 12–14에서 약 1,500대국/시간"도 실측이 아니라 정상상태의 낙관적 추정이다.
  - 이 실험이 증명한 것: worker 1 대 12의 논리 결과가 같고, 6 / 8 / 10 / 12 / 14가 20판 모두 같다. 즉 worker 수가 self-play의 의미를 바꾸지 않는다.
  - c1은 측정 규칙대로 worker 6으로 한다(사용자 승인). 처리량 도구 개선은 c1 뒤로 미룬다.
- CPU 사용률 21–27%도 worker 대부분이 시작 · 꼬리 동안 쉬고 있었다는 뜻이다.
  - torch는 worker당 1스레드다. 12600K는 16스레드이므로, 14 worker가 계속 바빴다면 80% 이상이어야 한다.
- 수당 시간은 worker가 늘수록 길어진다(0.58 → 0.82초, CPU 경합). 그래도 동시 대국 수 증가가 더 커서, 정상상태 처리량은 worker 12–14에서 약 1.6배로 추정된다.
  - 이 추정은 낙관적일 수 있다. 꼬리 구간에는 동시 대국이 적어 수당 시간이 덜 경합된 값이다.
- 결론
  - 측정은 규칙대로 했고 `workers = 6`은 규칙의 결과로 유효하다.
  - 그러나 "6이 가장 빠르다"는 1,000국 주기의 처리량을 말하지 않는다.
  - worker 수는 결과를 바꾸지 않으므로(재현성 PASS) 데이터 의미에는 영향이 없다. 바뀌는 것은 주기 시간뿐이다(1,000국: 약 1시간 대 40분 안팎).
- 측정 설계의 잘못(대국 수가 worker 수에 비해 적고, wall에 시작 비용이 들어감)은 도구의 것이다.
  - 고칠 방법: worker마다 대국을 충분히(예: worker × 8), 처리량은 모든 worker가 준비된 뒤부터
  - 주기 시간이 판정에 영향을 주지 않으므로, c1은 6으로 시작하고 도구 수정 · 재측정은 c1 뒤로 미뤄도 된다.

**초안에서 고칠 것 2: 외부 앵커의 정체.**
- 동결된 앵커는 Windows 빌드 `pbrain-rapfi-windows-avx2.exe`다.
  - Rapfi `0.43.01 (clang++ 19.1.5 on Windows SSE41 AVX2)`, SHA-256 `1e02497433fb…`
  - 같은 폴더의 config · 가중치 6개(external-engine.md §8.2)

**초안에서 고칠 것 3: Pre-RL 기준선의 seed.**
- X2는 "주기 c에 seed 8710 + c(c = 1…10)"이고, runner의 예약 블록(`evaluation.external`)은 8711–8720이다. c = 0에 해당하는 8710은 블록에 없다. 그래서 지금 runner는 8710을 거부한다(예약 밖 seed).

**우분투(데스크톱 WSL2)에서 Rapfi**
- 어댑터와 runner는 OS 중립이다: stdin/stdout pipe, 읽기 스레드로 timeout, `\r\n` 제거, `cwd` = 실행 파일 폴더, `run_signature`에는 파일 경로가 아니라 해시만 들어감.
- **Linux용 Rapfi로 바꾸면 다른 앵커다.** 실행 파일 SHA가 다르고, 컴파일러 · SIMD가 다르면 노드 제한 탐색의 수도 달라질 수 있다. 그때는 X1을 다시 해야 한다.
- **같은 Windows 실행 파일을 WSL2 interop으로 그대로 실행하면 코드 수정 없이 같은 앵커다.** `--engine /mnt/c/engines/rapfi/pbrain-rapfi-windows-avx2.exe`
  - `command[0]`가 그 파일이라 SHA(`1e02497433fb…`)가 그대로 기록된다.
  - `cwd`(`/mnt/c/engines/rapfi`)는 Windows 경로로 바뀌어 Rapfi가 `config.toml`을 찾는다.
  - `--engine-file`은 해시만 signature에 들어간다.
- 실행 전 확인(사전 고정)
  1. `sha256sum`이 실행 파일 · 6개 파일 모두 §8.2와 같은가
  2. **규칙 교차검사 재현:** `external_rule_crosscheck.py` seed 1 · 반경 1 · 300판이 데스크톱 Windows 기록과 같은가(8,886국면, 금수점 9,517, 불일치 0). 우리 쪽 무작위 수만 쓰므로 Rapfi 답만의 비교다.
  3. **X1 재현성 재실행:** `tb1` 대 L_mid, seed 8703, 2쌍. fingerprint가 Windows의 `1adbb7d3433bb330…`와 같은가
     - 같으면 WSL 경로가 Windows 경로의 대국을 그대로 재현한 것이다.
     - 다르면 원인이 우리 쪽(`tb1`의 CPU torch, OS 차이)인지 Rapfi인지 2번 결과로 가른다.
     - 8703은 X1 재현성 seed라 학습 데이터와 무관하다.
  4. 끝난 뒤 `tasklist.exe | grep -i rapfi`로 남은 Windows 프로세스가 없는가
- 같은 기계에서 다른 측정과 동시에 돌리지 않는다(§8 원칙). Pre-RL은 c1 self-play 전에 따로 한다.

**Pre-RL 기준선에 필요한 코드 (제안)**
1. `run_external_match.py --ours tbv3`
   - canonical factory(`canonical.factory('TB-V3', 'fast5')`, 동결 H3 / H6, `--value-device cuda`)로 만든다.
   - worker마다 fast4 → fast5 binding, 모델 검사
   - provenance: 엔진 해시, runtime 해시(장치별), 모델 SHA 4개 → `run_signature`
   - `check_track_b_frozen`과 같은 fail-closed. 동결 모델이 아니면 거부한다.
2. seed 8710을 X2 cycle 0으로 등록한다(위).
3. c1 뒤 X2(cycle c의 후보 모델)는 `tb_v3_net` 경로가 필요하다. 그 factory는 `scripts/h7c_*`만 쓸 수 있으므로 `scripts/h7c_external.py`(runner를 감싸 후보 모델 identity를 기록)로 둔다. c1 checkpoint가 생길 때 만든다.

**사전 고정 (Pre-RL 전에)**
- Pre-RL 결과를 본 뒤 c1의 학습 설정(λ, target, 표본, 주기 규칙, worker 외 모든 것)을 바꾸지 않는다.
- Rapfi 강도(L_mid 300 / L_strong 1000)도 바꾸지 않는다.
- 설정: L_mid 25쌍(50판), seed 8710, `--forbid-check`, opening 4수 · 반경 2, `--workers 4`(X1과 같음)
- 보고: score, 쌍 bootstrap 95%, Elo, 색별, 평균 길이, illegal / error, 금수점 불일치, loss 후보
- 비교 주의: X2는 주기마다 seed가 달라(opening이 다르다) 주기 사이 차이에 opening 표본 잡음이 들어간다. 진단 지표로만 읽는다.

## Pre-RL Rapfi 기준선 (승인 2026-10-23, 대국 전 고정)

**구현**
- `run_external_match.py --ours tbv3`

**policy fine-tune (`configs/h7c/c1_policy.json`, `scripts/h7c_train_policy.py`, `hybrid.h7c_train.train_policy`)**

| 항목 | 값 |
|---|---|
| 시작 / teacher | 시작은 cycle의 parent(c1: H3)다. KL teacher와 guard 기준은 언제나 동결 H3다. |
| 손실 | 행마다 CE(target, student) + 0.5 · [visits 행] · KL(H3 ‖ student). 합법 수 위 masked softmax, T = 1. teacher는 같은(D4 증강된) planes에서 계산한다. |

| warmup | 전체 step의 5%(최소 5, 최대 100), 그 뒤 cosine으로 0.05까지 |
| BatchNorm | **running 통계는 parent 그대로(eval 모드)**, 가중치는 모두 학습. 몇백 step의 1주기 데이터로 guard가 재는 통계를 다시 추정하지 않기 위함이다(2026-10-24 승인, H7 전체 규칙). |
| 평가 | 전체 step에서 고르게 10번 |
| guard · best | 평가마다 c1 val 목적함수와 RenjuNet H3 val top-1(전체 split)을 잰다. H3보다 2%p 넘게 떨어지지 않은 평가만 후보다. 그중 c1 val 목적함수가 가장 낮은 것이 best다. 후보가 없으면 `NO_CANDIDATE`(checkpoint 없음). |
| 산출 | policy-only `best.pt` + `best.json`(`RootPolicy`와 `tb_v3_net`이 받는다), `record.json` |

| 항목 | 값 |

## H7-c1 학습 · Arena 계약 검토 및 승인 (2026-10-24, 사용자 검토 `d0d4b4f` · `b9492b3`)

`d0d4b4f`의 policy/value 학습 및 provenance 도구와 `b9492b3`의 Arena·tactical gate·X2 구현을 검토하였다.

Policy 학습의 CE + KL(H3‖candidate), RenjuNet top-1 −2%p guard, 5% warmup, D4 augmentation과 guard 통과 checkpoint 중 cycle validation objective 최소값을 선택하는 방식에 동의한다.

Policy fine-tuning 중 BatchNorm running statistics는 cycle parent의 값을 고정한다. BN affine parameter를 포함한 network parameter는 학습하되 running mean/variance는 재추정하지 않는다. H7의 짧은 cycle fine-tuning에서 기존 RenjuNet representation의 inference statistics를 보존하기 위한 규칙으로 H7 전체에 고정한다.

Value는 직전 champion의 value head에서 이어서 학습하고 trunk와 policy head는 고정한다. 새 cycle value rows와 frozen H6-v3 replay anchor를 epoch마다 50:50으로 사용하며 proof 1.0 / outcome 0.1 weight를 유지한다. 기존 H6 validation weighted MSE가 parent 기준 1.05배를 넘는 checkpoint는 후보에서 제외한다. 1.05 값은 H7 결과를 확인한 뒤 변경하지 않는다.

H7의 value replay anchor는 모든 cycle에서 frozen H6-v3 cache로 고정한다. Cycle별 새 데이터는 변경되지만 기존 지식 보존용 replay source는 바꾸지 않는다. Candidate metadata에는 cycle label SHA와 replay-anchor label SHA를 별도 필드로 기록하고, 다음 cycle에서 이를 fail-closed로 검증한다.

Internal Arena는 기존 Track B 계약대로 candidate와 직전 champion의 50쌍 대국을 공식 승급 평가로 사용한다. Promotion 조건은 score > 0.50, pair-bootstrap 기준 `(score − 0.50)`의 95% 하한 ≥ −0.05, tactical gate PASS를 모두 만족하는 경우로 고정한다. P-only/V-only 각 25쌍과 고정 Monitoring 상대 3종 각 25쌍은 진단용이며 승급 판정에는 사용하지 않는다.

Tactical hard gate는 다음과 같이 고정한다.

- candidate illegal move 0
- `unsound_witness` 0
- P93/P94 value sign PASS
- must_block ≥ 9/40
- must_block ≥ parent − 2 hits

E1의 rescue_rate, veto_recall, false_veto 및 기타 비율 지표는 parent와 함께 기록하지만 cycle promotion의 hard gate로 사용하지 않는다. Official Arena에서 parent가 illegal move를 둔 경우 해당 승리를 candidate score에 정상 승리로 사용하지 않고 Arena를 invalid로 처리하여 승급을 금지한다.

Monitoring의 Elo는 cycle별로 각 고정 상대에 대한 상대 Elo로 기록한다. 서로 다른 상대의 Elo를 하나의 공통 Elo로 직접 비교하지 않는다. Cycle 2 이후 누적된 고정 상대 대국을 이용한 Bradley–Terry 공통 척도는 별도 monitoring 분석으로 계산한다.

X2 Rapfi 평가는 cycle `c`에 seed `8710 + c`, L_mid 25쌍으로 고정하며 기록 전용이다. Rapfi 결과는 내부 promotion에 사용하지 않는다.

Cycle provenance는 fail-closed로 유지한다. 학습 입력의 self-play model SHA와 trainer parent SHA가 일치해야 하며, candidate policy/value metadata의 cycle은 실행 cycle과 같아야 한다. Cycle 2 이후 parent는 직전 cycle verdict가 지정한 champion identity와 일치해야 한다. X2에도 동일한 candidate-cycle 검증을 적용한다.

Policy 또는 value 학습에서 `NO_CANDIDATE`가 발생하면 Arena를 강제로 실행하지 않는다. 대신 해당 cycle을 `KEEP_CHAMPION / NO_CANDIDATE`로 기록하여 cycle history를 연속적으로 유지하고, 해당 cycle은 수렴 조건의 연속 정체 cycle로 계산하지 않는다.

WSL external-anchor gate는 기존 executable·engine-file SHA, rule crosscheck, X1 run signature, game fingerprint와 함께 crosscheck 및 reproducibility run이 clean git tree에서 생성되었는지도 확인한다.

위 보강 사항과 WSL gate evidence가 커밋되고 데스크톱의 frozen checker 및 관련 테스트가 모두 PASS하면 H7-c1 self-play 1,000판을 `workers=6`, run seed `8801`로 시작하는 것을 승인한다.

- **수렴 해석:** 향상 하한이 null인 cycle(`NO_CANDIDATE`, 공식 arm invalid)은 정체로 세지 않는다.
  - "연속 2주기" 조건은 마지막 두 cycle이 모두 하한 ≤ 0이어야 하므로 null cycle이 사이에 있으면 연속이 끊긴다.
  - 최소 3주기 조건은 끝낸 cycle 수(null cycle 포함)로 센다.
