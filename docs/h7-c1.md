## 브랜치 (2026-10-23 사용자 승인)

```
feat/h6-value              [동결] H6, TB-V2-Value, E4-v2, TB-V3 Resolve, fast5 G0 / G1 / G2, SER5 · CPU 인증,
│                                 근거 검사, tb_v3_net factory, H7-c1 설계 계약 (b0aad75)
├── feat/h7-c1             학습 계보: self-play, label, policy / value 학습, 후보 Arena, 다음 checkpoint
└── (병합으로만) feat/Web_SER5 -> feat/Web_SER5-tbv3-fast5   배포 계보: 웹, 세션, DB, Caddy / systemd
```

- `feat/h6-value`는 동결 기준점이다. 허용되는 변경은 오탈자, 기존 결과의 설명 보완 같은 비실행 문서 변경뿐이다. 엔진 · runtime · 모델 identity에 닿는 변경은 하지 않는다.
- 이 브랜치(`feat/h7-c1`)는 canonical 엔진 · runtime을 바꾸지 않는다.
  - self-play의 실행판은 TB-V3 Resolve / fast5다.
  - 새 모델은 `analysis.tb_v3_net` 후보 identity로만 쓴다.
- 새 checkpoint는 canonical, SER5 웹, benchmark 기준으로 자동 승격하지 않는다. Arena와 승급 gate, 별도 promotion 단계에서만 정한다.
- 웹 계보의 병합 결과는 이 브랜치로 가져오지 않는다. 반대로 학습 코드도 웹 계보로 보내지 않는다.

## 고정된 설계

`docs/h6-value.md`, "H7-c1 설계 승인과 0 · 1번 구현"이 계약이다.
- 두 망
- KL(H3 ‖ c1) λ = 0.5. 보통 국면에만 적용하고 증명 one-hot에는 적용하지 않는다.
- top-1 guard −2%p
- run seed 이름 공간 8800–8999. 대국 seed = `derive_seed(run_seed, 'h7c', cycle, game_index)`

- `h6_labels` 재사용

## 구현 1–3, 5 (2026-10-23)

**`src/hybrid/h7c_targets.py`: target과 표본 규칙(생성기와 label 단계가 같은 함수를 쓴다)**
- TB-V3의 route 분류
  - 증명된 승리: `stage1`(지금 오목), `stage3`(막을 수 없는 사), `own_vcf`, `own_vct`(V8-B), `own_vct2`(E4-v2)
  - tree: `v8_root_visits`에 root 자식의 (수, 방문, 평균값)이 있다.
  - 강제 수: `stage2`(오목 막기), `stage4` / `stage5`(강제 방어). tree가 돌지 않아 방문 분포가 없다.
- 증명된 패배 후보: 그 수에서 root · VCT2 · stage-VCT 검사가 `UNSAFE`(PROVEN_LOSS_VCT1)로 판정한 수
- policy target
  - `proof_one_hot`: 증명된 승리 route. 둔 수에 확률 1, KL 없음
  - `visits`: tree의 방문 분포에서 증명된 패배를 0으로 두고 다시 정규화. KL 적용
  - `none`: 강제 수, 또는 방문이 모두 증명된 패배인 경우. policy loss 없음
  - 원본 방문 수(`[행, 열, 방문, 평균값]`)는 항상 함께 남는다.
- 표본(opening 뒤 처음 4수, T = 1)
  - 증명된 승리는 그 수를 둔다(`proven_win`).
  - tree는 위 분포에서 뽑는다(`sampled`).
  - 그 밖에는 엔진의 수를 두고 기록한다(`no_distribution`).
- 강제 수(`stage2` / `stage4` / `stage5`)의 policy target은 `none`이다(policy 학습에서 뺌, value 라벨은 남음). 사용자 승인으로 확정했다(아래 "승인 보충").

**`scripts/h7c_selfplay.py`: 생성기**
- 엔진: 양쪽 모두 `tb_v3_net.make_tb_v3_net_agent`(동결 TB-V3 / fast5, 후보 모델). 대국마다 색별 agent 하나(E4-v2 cooldown이 agent마다 있다)
- seed
  - 학습 run seed는 8801–8999다. 8800은 처리량 측정 전용이라 생성기가 학습 run에는 거부한다.
  - 대국 seed = `derive_seed(run_seed, 'h7c', cycle, i)`, opening seed = `derive_seed(run_seed, 'h7c-opening', cycle, i)`
  - 충돌 · 예약 seed를 검사한다.
- 대국마다 남기는 것
  - run identity: 엔진 해시, value 장치의 fast5 runtime 해시, 모델 SHA 4개와 그 해시, `frozen_models`, opening · 표본 · target 형식
  - 코드 커밋, opening, 결과(`real_draw`는 판이 다 찬 무승부만)
  - 수마다: route, 엔진의 수 / 둔 수, 표본 사건, 원본 방문, 증명된 패배, policy target, E4 실행 여부
- 이어하기: 끝난 index는 건너뛴다. 다른 run(seed, cycle, 모델, 엔진, runtime, 규칙)의 파일은 거부한다.
- 더러운 tree는 거부한다. 진행 출력은 1분마다(`run_chunks`)다.
- 테스트: 무작위 망(동결 구조)의 실제 후보 agent로 대국을 둔다. 같은 seed면 같은 대국이고, 이어하기 · 거부도 확인한다.

**`scripts/h7c_labels.py`: label 단계 (H6 규칙 재사용)**
- 증명: `build_h6_labels`의 proof task와 같은 예산. 증명 1.0, 결과 0.1이고, 증명이 결과보다 우선한다.
- value 행은 H6 행 형식 그대로다. 그래서 `h6_value_cache` / `h6_value_train`이 바로 읽는다.
- probe
  - probe 국면이 든 대국은 통째로 뺀다(`default_probe_files` + `--probe-files`로 웹 probe 추가).
  - 3수 opening probe만 행 단위 mask다(H6-v2 규칙).
- split: 대국 단위(`split_for`, salt `h7c-v1`, val 5%). 뒤 split의 중복 국면은 mask하고 `check_leakage`를 통과해야 한다.
- 입력 검사: 한 cycle · 한 모델, 학습 run seed만, 잘린 대국 없음, 중복 없음, 수와 수별 기록이 일치
- policy 행(`h7c-policy-row-v1`): target 종류, KL 여부, target, 원본 방문. probe 행 · 뒤 split 중복은 value 행과 같이 mask한다.
- 출력은 `data/`나 `runs/` 아래로만 쓴다.

**`scripts/h7c_throughput.py`: worker 재현성과 처리량 (운영 값)**
- `repro`: run seed 8800, 4국을 worker 1과 12로 두고, 시간 외 모든 기록이 같아야 `REPRO_PASS`다.
- `sweep`: 같은 20국을 worker 6 / 8 / 10 / 12 / 14로 둔다.
  - 기록: 시간당 대국, 수 평균 · p99, GPU 사용률 · 메모리(nvidia-smi), CPU 사용률
  - 선택: 최고의 95% 안에서 가장 적은 worker
- 이 환경에서 무작위 망으로 worker 1 / 2 비교 `REPRO_PASS`를 확인했다(테스트).

**실행 명령 (데스크톱, `feat/h7-c1`)**

```bash
cd ~/renju-h6 && git fetch origin && git checkout feat/h7-c1 && git pull --ff-only && source .venv/bin/activate
export PYTHONUNBUFFERED=1 PYTHONPATH="$PWD/src"
(cd src && CC=gcc python -m rt30.native.build --if-stale && python -m rt30.vcfcore.build --if-stale)
python scripts/check_track_b_frozen.py
python -m unittest tests.test_h7c_selfplay tests.test_h7c_labels tests.test_tb_v3_net
POL=runs/h3_policy_64x4/best.pt; VAL=runs/h6_value_head_v3/best.pt
mkdir -p docs/h7c
python -u scripts/h7c_throughput.py repro --policy-checkpoint $POL --value-checkpoint $VAL --device cuda \
  --out runs/h7c/throughput_repro --output docs/h7c/h7c1_repro.json
python -u scripts/h7c_throughput.py sweep --policy-checkpoint $POL --value-checkpoint $VAL --device cuda \
  --out runs/h7c/throughput_sweep --output docs/h7c/h7c1_throughput.json 2>&1 | tee runs/h7c/throughput_sweep.log
```

- 커밋할 것: `docs/h7c/h7c1_repro.json`, `docs/h7c/h7c1_throughput.json`. jsonl은 `runs/`에 둔다.
- 측정 대국 수는 기본 설정에서 108국이다: repro 8국(worker 1 × 4, worker 12 × 4) + sweep 100국(5 설정 × 20국). 대국 길이에 따라 다르지만 한두 시간 안쪽으로 예상한다.
- 측정은 이 도구들의 최종 커밋에서 한다. 생성기 커밋이 run identity에 들어가므로, 측정 JSON이 그 커밋의 증거다.
- cycle 1 생성(1,000국)은 학습 단계가 준비된 뒤에 시작한다. 생성기만 먼저 돌려도 되지만, 학습 · label 규칙이 바뀌면 다시 둘 수 있게 하려는 것이다.

## 승인 보충 (2026-10-23, 구현 검토 반영)

**seed 이름 공간 (원 승인의 8800–8999를 나눈다)**
- 8800: worker 재현성 · 처리량 측정 전용(`scripts/h7c_throughput.py`). 이 대국은 학습 데이터가 아니다. 생성기는 8800으로 학습 run을 거부하고, label 단계도 거부한다.
- 8801–8999: 학습 run seed. 대국 seed는 `derive_seed(run_seed, 'h7c', cycle, i)` 그대로다.

**강제 수 policy target: `none` (승인)**
- 이유: `stage2`는 상대 오목 후보가 여럿일 때 그중 하나를 고르고, 방어 route는 heuristic tie-break의 영향을 받는다. one-hot으로 배우면 강제 규칙이 아니라 기존 엔진의 임의 tie-break를 외울 수 있다.
- 나중에 "합법 방어가 정확히 하나"임을 증명하는 route가 생기면 그 경우만 one-hot으로 넓힌다.

**`91856ad` 검토에서 고친 것 (사실 확인 뒤)**
1. policy 행의 probe mask
   - 문제: value 행(기본 `from_ply` 5)을 거쳐 mask를 정했다. 그래서 ply 3의 opening probe가 policy 행에 남았다.
   - 수정: 이제 probe 해시로 직접 mask한다. 기본 `from_ply`로 회귀 테스트를 추가했다.
2. 생성기 커밋
   - 문제: 대국에는 기록됐지만 run identity에는 없었다. 그래서 같은 파일에 다른 코드의 대국을 이어 쓸 수 있었다.
   - 수정: 이제 `generator_git`(커밋, dirty)이 identity에 들어간다. 이어하기는 정확히 일치해야 하고, label 단계는 커밋이 하나이고 깨끗해야 한다.
3. label 단계의 target 재검증
   - 문제: 저장된 target을 그대로 썼다.
   - 수정: 이제 route · 엔진 수 · 방문 · 증명된 패배로 `policy_target`을 다시 계산해 정확히 비교한다. 확률 ≥ 0, 합 1, 증명된 패배 0, 증명 one-hot, 강제 수 none도 확인한다.
   - 표본 사건도 검사한다(처음 4수: sampled / proven_win / no_distribution, 그 뒤: engine).
4. 행 provenance
   - 이제 value · policy 행마다 `h7c_provenance`를 남긴다: runtime 해시, 모델 SHA 4개, self-play 커밋, label 커밋.
   - `h6_value_cache`는 H6 필드만 읽고 나머지는 무시한다. 테스트로 실제 reader 통과를 확인했다.
5. sweep fail-closed: 어느 worker 수라도 대국이 첫 설정과 다르면 `SWEEP_REPRO_FAIL`이다. `chosen_workers`는 없고 exit 1이다.
6. 이어하기 파일
   - 같은 index가 두 번 나오거나 중간 줄이 깨졌으면 거부한다.
   - 마지막 줄만 깨졌으면(append 중 종료) 알리고 그 줄을 잘라 낸 뒤 그 대국을 다시 둔다.
7. label 입력 재생: 수순 순서, 둘 차례, 모든 수의 합법성, 길이, 최종 승자 · 결과 · real_draw가 일치해야 한다.
8. label 산출물은 `.tmp`에 다 쓴 뒤에만 제자리로 옮긴다(실패하면 아무것도 남지 않는다).
9. 테스트: `unittest.main()` guard를 파일 끝으로 옮겼다. 표본 결정론은 같은 seed의 두 RNG로 200번 뽑은 전체 수열을 비교한다.

- 확인: 위 회귀 테스트를 포함해 관련 59개 PASS(동결 모델이 필요한 2개 skip). 이 브랜치에는 CI가 돌지 않으므로(main · PR만) 이것은 로컬 결과다.
- 순서: 이 수정 커밋 → 데스크톱 repro(같은 커밋) → `REPRO_PASS`면 sweep → 측정 JSON 커밋 → 학습 구현
