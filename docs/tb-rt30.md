# TB-RT30: 착수 30초 서버 엔진 설계

- 상태: 설계안(코드 없음). 2026-10-14.
- 기준 엔진: `TB-Engine-v1`(`src/analysis/tb_engine_v1.py`, E3-A). **바꾸지 않는다.**
- 대상 하드웨어: Beelink SER5 MAX, Ryzen 7 5800H(8코어 16스레드).
- 시간 규칙: 엔진 안 소프트 마감 27~28초, 서버 하드 워치독 29초.

## 0. 요약

1. TB-RT30-v1은 TB-Engine-v1의 **설정과 판단 규칙을 그대로 쓰고**, 시간만 예산처럼 다루는 파생 엔진이다.
   마감에 걸린 검사는 지금의 예산 소진과 똑같이 `UNKNOWN`이 된다. v1의 모든 규칙은 이미 `UNKNOWN`을
   보수적으로 처리하므로(증명되지 않은 공격은 두지 않고, 증명되지 않은 패배로는 거부하지 않는다) 새 판단 규칙이 필요 없다.
2. **마감에 닿지 않은 수는 TB-Engine-v1과 같은 수**다. 이것이 첫 번째 테스트 gate다.
3. 시간을 노드 수로 바꿔 VCF 호출 하나하나의 상한에 넣는다. 지금 코드는 초당 약 1,600노드라서
   20,000노드짜리 VCF 호출 하나가 12초까지 걸릴 수 있다. 호출 사이에서만 시계를 보면 마감을 지킬 수 없다.
4. 엔진은 단계마다 "지금 두면 둘 수"(provisional move)를 서버에 보낸다. 29초 워치독이 터지면 서버는
   마지막 provisional move를 두고 worker 프로세스를 교체한다.
5. 지난 E3/E1-holdout 기록 4,828수로 추정하면 **약 20%의 수(948수)가 어딘가에서 마감에 걸린다**(측정 환경 기준).
   5800H가 그 환경보다 1.5배 빠르면 14%, 2배면 12%다. 그래서 구현 전에 5800H 실측(§7)이 먼저다.

## 1. 범위

- 하는 것: 마감을 지키는 엔진(`TB-RT30-v1`), 서버 쪽 worker·워치독·대체 수, 검증 gate.
- 하지 않는 것: TB-Engine-v1 수정, 예산(노드 수) 재조정, 병렬 탐색. 예산을 줄이거나 병렬로 바꾸면
  판단 자체가 달라지므로 TB-RT30-v2 후보로 따로 둔다(§9).
- CLAUDE.md의 동결 파일(`tb_engine_v1.py`, `mcts_v8.py`, `e3_arms.py`, `s3_vct2_v1.py`, `puct_v8.py`, `threats.py`)은
  import만 하고 고치지 않는다.

- V8-B가 WIN을 찾은 134수 중 공격 검사가 9초 안에 끝난 것은 62수, 15초 안은 80수, 27초 안은 95수다.

## 3. 설계 원칙

1. **시간 절단 = 예산 절단.** 마감에 걸린 검사는 캐시하지 않고 `UNKNOWN`으로 끝난다. `_BudgetedSolver`가
   총예산에 걸렸을 때와 같은 경로(`_BudgetExhausted`)를 쓴다.
2. **마감 전에는 v1과 같은 수.** 같은 국면, 같은 seed, 마감 무한대이면 TB-RT30-v1의 수 = TB-Engine-v1의 수.
3. **언제나 둘 수가 있다.** 엔진은 첫 수십 ms 안에 provisional move를 하나 갖고, 단계가 끝날 때마다 바꾼다.
4. **이중 안전장치.** 엔진은 27.5초에 스스로 멈추고, 그래도 안 끝나면 서버가 29초에 끊는다.
5. **기록이 재현을 대신한다.** 시간 절단은 실행마다 달라질 수 있다. 그래서 절단이 어느 단계, 몇 번째 VCF 호출에서,
   얼마의 노드 상한으로 일어났는지 기록해서 같은 수를 다시 만들 수 있게 한다(§5.5).

## 4. 시간 예산

기준 시각 `t0`는 **서버가 요청을 받은 순간**(monotonic clock)이다. 엔진은 상대 시간이 아니라 절대 마감 시각을 받는다.

| 이름 | 기본값 | 의미 |
|---|---|---|
| `D_soft` | t0 + 27.5초 (27.0~28.0 설정) | 엔진이 새 검사를 시작하지 않고 결과를 내는 시각 |
| `D_hard` | t0 + 29.0초 | 서버 워치독. 응답이 없으면 provisional move를 둔다 |
| 여유 | 1.5초 | 진행 중인 VCF 호출의 초과분, 프로세스 간 통신, 직렬화 |

### 4.1 단계별 마감 (tree 경로 기준)

v1의 순서는 그대로 두고, 각 단계가 남은 시간의 몫만 쓰게 한다. `now`는 그 단계가 시작된 시각이다.

| 단계 | 단계 마감 | 이유 |
|---|---|---|
| stage 1–3, 자기 VCF | `D_soft` (사실상 3초 안) | 비용 상한이 작다. 따로 자르지 않는다 |
| V8-B 공격 | `now + 0.40 × (D_soft − now)` | 공격 실패는 기회 손실, 뒤 단계 실패는 패배 위험. 뒤를 굶기지 않는다 |
| V8-A(stage 4/5) | `D_soft` | 이 경로에는 뒤 단계가 없다 |
| root 후보 준비 + tree | 시작 조건: `D_soft − now ≥ 6초` | 5초 상한. 부족하면 tree를 건너뛰고 policy 1순위(안전 tier 안)를 둔다 |
| V8-C root 검사 | `now + 0.60 × (D_soft − now)` | V7 수가 먼저 예산 절반을 받는 v1 규칙은 그대로 |
| VCT2 veto | `D_soft` | `UNKNOWN`은 거부하지 않으므로 절단은 "검사 안 함"과 같다 |

V8-B가 일찍 끝나면 남은 시간은 자동으로 뒤 단계로 간다(몫이 "남은 시간" 기준이므로).

### 4.2 추정 영향 (§2.2 기록에 위 몫을 적용한 시뮬레이션)

| 5800H 속도(기록 대비) | 절단이 생기는 수 | V8-B 절단 | V8-A 절단 | V8-C 절단 | VCT2 절단 |
|---|---|---|---|---|---|
| 1.0배 | 948 / 4,828 (19.6%) | 343 | 109 | 354 | 481 |
| 1.5배 | 683 (14.1%) | 294 | 85 | 284 | 278 |
| 2.0배 | 558 (11.6%) | 261 | 74 | 257 | 169 |

판단이 바뀔 수 있는 절단(위의 부분집합, 상한 추정): 1.0배에서 V8-B WIN 놓침 67, V8-C 교체 착수 89(95 중),
V8-A 교체 착수 45, VCT2 교체 2. V8-C 교체 착수는 대부분 400k 예산을 다 쓰는 국면이라 절단돼도 같은 수가 나올 수 있다.
실제 영향은 §8의 재생으로 잰다. 시뮬레이션 스크립트는 기록의 단계별 시간을 순서대로 더하는 근사다.

### 5.1 파일

| 파일 | 내용 |
|---|---|
| `src/analysis/tb_rt30_v1.py` | 이름, `TB_ENGINE_V1`를 그대로 가져온 설정 + RT 설정(`D_soft`, 몫, tree 최소 시간), `config_hash`, `make_engine` |

| `tests/test_tb_rt30_v1.py` | 설정 동일성, 마감 무한대 동치, 절단 의미 테스트 |

`mcts_search_v8`의 상위 흐름(약 120줄)과 solver를 직접 만드는 세 함수(`_own_vct_attack`, `_verify_root_choice`,
`_vct2_veto`, 합 약 90줄)는 solver 생성만 바꿔서 `mcts_rt.py`에 옮긴다. 나머지(`_proven`, `_first_proven`,
`_stage_vct_move`, `prepare_root_moves`, `search_tree_puct` 등)는 import해서 그대로 쓴다. 복사한 부분이 v1과 어긋나지 않는지는
§8 G0 테스트가 지킨다.

### 5.2 시간을 노드 상한으로 바꾸기

`_BudgetedSolver.vcf`는 이미 호출마다 `limit = min(node_limit, 남은 예산)`을 계산하고, 총예산 때문에 잘린 호출은
`_stop()`으로 올려 보낸다. `DeadlineSolver`는 여기에 세 번째 상한만 더한다.

```python
limit = min(self.node_limit, remaining_budget, self.deadline.node_cap())
# node_cap() = floor((phase_deadline - now) * rate.safe())
```

- `limit`이 시간 상한 때문에 작아졌는데 그 안에 결론이 안 나면 `_stop()`과 같은 경로로 올라간다.
  캐시되지 않고, 그 검사는 `UNKNOWN`이 된다.
- 마감이 지나면 `exhausted = True`, `deadline_cut = True`로 둔다. 이후 `_bounded`는 곧바로 `UNKNOWN`을 낸다(v1 코드 그대로).
- 시간 상한이 다른 두 상한보다 크면 결과는 v1과 같다. 마감 무한대 동치는 여기서 나온다.
- 결과에 따라 `exhausted`(총예산)와 `deadline_cut`(시간)을 따로 기록한다.

`SelectiveSolver`(VCT2)도 `_BudgetedSolver`의 자식이므로 같은 방식으로 `DeadlineSelectiveSolver`를 만든다.

### 5.3 속도 추정 (`RateEstimator`)

- worker가 뜰 때 고정 VCF 벤치마크(약 0.5초)로 초기값을 잰다.
- 이후 VCF 호출마다 `(노드, 초)`를 넣어 최근 값의 하위 10% 분위를 `safe()`로 쓴다. 느리게 잡을수록 마감은 지키고 탐색은 줄어든다.
- 하한을 둔다(예: 500노드/초). 노드 상한이 0이 되지 않게 최소 1노드는 준다.

이 방식의 남은 초과분은 "실제 속도가 `safe()`보다 느렸던 만큼"뿐이다. 1.5초 여유가 이것을 흡수한다.

### 5.4 고정 비용 단계

자기 VCF(5,000노드), root 후보의 V7 안전 tier(8,000노드), stage 4 V7 tier, tree는 동결 함수 안에서 돌고 상한이 작다.
이 단계들은 자르지 않고, **시작 전에 남은 시간이 기준(예: 6초)보다 적으면 건너뛰고** provisional move를 둔다.
v1 기록에서 이 단계들의 합은 수 초 안이라 정상 착수에서는 건너뛸 일이 없다.

### 5.5 provisional move와 진단

엔진은 단계가 끝날 때마다 `(move, source)`를 콜백으로 낸다.

| 시점 | provisional move |
|---|---|
| 시작 직후 | 5목 완성 > 상대 5목 막기 > H3 policy 1순위 합법수 |
| stage 1–3 / 자기 VCF / V8-B WIN | 그 수(최종) |
| stage 4/5 | V7 강제 방어수, V8-A가 끝나면 그 결과 |
| root 후보 준비 후 | 안전 tier 1 안의 policy 1순위 |
| tree 후 | tree 수(V7 수) |
| V8-C 후 / VCT2 후 | 각 단계 결과 |

진단(`SearchDiagnostics` 확장): `rt_deadline`, `rt_phase_deadlines`, `rt_cut_phase`, `rt_cut_call_index`,
`rt_cut_node_cap`, `rt_rate_safe`, `rt_skipped_phases`, `rt_provisional_trail`. 기존 v8 진단 필드는 그대로 채운다.
`rt_cut_*`가 있으면 "그 호출에 그 노드 상한"을 주는 재생 모드로 같은 수를 다시 만들 수 있다.

### 5.6 seed

v1 agent는 판 전체에서 `Random` 하나를 이어 쓴다. 서버는 요청마다 상태가 없어야 하므로(worker 교체 때문에)
요청마다 `seed = hash(game_id, ply)`로 새 `Random`을 만든다. 동치 테스트도 같은 seed의 새 v1 agent와 비교한다.

## 6. 서버 설계

### 6.1 프로세스 구조

```
HTTP 요청 ─▶ 서버(메인 프로세스, 워치독)
                 │  요청: (국면, game_id, ply, D_soft 절대시각)
                 ▼
            worker 프로세스 (엔진 1개, torch 1스레드)
                 │  provisional 메시지 ... 최종 메시지
                 ▼
            서버: 최종 수 또는 29초에 마지막 provisional
```

- 엔진은 순수 Python CPU 작업이다. 스레드로는 멈출 수 없으므로 **반드시 별도 프로세스**로 돌린다.
- worker는 미리 띄워 둔다(H3 checkpoint 로드와 `check_checkpoint` 해시 확인을 시작 때 끝낸다). 대국 수만큼 + 예비 1개.
- `torch.set_num_threads(1)`. NN 호출은 착수당 3ms 수준이라 스레드를 늘릴 이유가 없고, 여러 worker가 코어를 나눠 쓴다.

### 6.2 워치독

- `D_hard`(t0 + 29초)까지 최종 메시지가 없으면 마지막 provisional move로 응답한다.
- 그 worker는 `terminate()`하고 예비 worker로 바꾼 뒤 새 예비를 띄운다. 엔진 상태가 요청 밖에 없으므로 잃는 것이 없다.
- provisional도 없으면(worker가 죽은 경우) 서버가 직접 대체 수를 고른다: 5목 완성 > 상대 5목 막기 > 열린 4 막기 >
  중앙에 가까운 합법수. 흑 금수는 `Game.legal_moves()`로 거른다.
- 워치독 발동은 항상 로그에 남기고, 운영 지표로 센다(목표 0회).

### 6.3 로그

기존 `run_web_play.py` 형식을 따른다: 엔진 이름, 설정 해시, checkpoint 해시, 커밋, 착수별 시간과 진단.
추가로 `t0`, 응답 시각, 워치독 발동 여부, provisional 출처, worker 교체를 남긴다.

## 7. Ryzen 7 5800H (SER5 MAX)

- 8코어 16스레드, 단일 코어 부스트 최대 4.4GHz. 미니 PC라서 여러 코어를 오래 쓰면 클럭이 내려간다.
  **동시 대국 수에 따라 노드/초가 달라진다.** `RateEstimator`가 실제 부하에서 재는 이유다.
- 동시 대국: 물리 코어 8개 중 서버와 OS 몫을 빼고 **최대 6개**에서 시작한다. SMT 16스레드를 다 쓰면 대국당 속도가 크게 떨어진다.
- 구현 전 첫 측정(코드 변경 없이 가능):
  1. TB-Engine-v1로 §2.2의 긴 수(28초 초과 850수 중 표본 100개)를 동시 1, 4, 6개로 재생해 노드/초와 착수 시간을 잰다.
  2. 그 속도 비율로 §4.2 표를 다시 계산하고, 몫(0.40 / 0.60)과 `D_soft`를 정한다.
- 운영체제(Windows / Linux)에 따라 worker 시작 방식이 다르다. Windows는 `spawn`이라 worker 시작이 느리므로 예비 worker가 꼭 필요하다.

## 8. 검증 gate

| gate | 내용 | 통과 조건 |
|---|---|---|
| G0 동치 | 마감 무한대로 고정 국면(fixture, E1-holdout suite, E3/E1h 기록 국면 표본)을 v1과 같은 seed로 비교 | 수 100% 일치, v8 진단 필드 일치 |
| G1 절단 의미 | 인위적으로 짧은 마감에서 절단 결과가 캐시되지 않고 `UNKNOWN`으로만 나오는지, 증명 결과(SAFE/UNSAFE/WIN)는 v1과 같은지 | 단위 테스트 |
| G2 지연 | 5800H에서 §7의 긴 수 표본과 실제 대국 200판, 동시 6판 | 엔진 응답 최대 ≤ 28.0초, 워치독 0회 |
| G3 안전 회귀 | E1-holdout suite(`e1h`)를 RT30으로 다시 판정 | unsound_witness 0, false_veto 0. RESCUED와 veto_recall의 감소는 사례별로 보고 |
| G4 대국 | RT30 대 v1(무제한), 같은 opening·seed 짝 | 승률 차이와 절단 수의 결과를 보고(통과 기준은 G2 뒤 사용자와 정한다) |

## 9. 다음 후보 (TB-RT30-v2, 이번 범위 밖)

- **병렬 V8-C / V8-B:** root 자식 4개 검사를 프로세스로 나눈다. 캐시를 공유하지 않으므로 v1과 수가 달라질 수 있다.
  VCT2는 검사가 거의 항상 1개(4,828수 중 2개 이상은 6수)라 병렬 이득이 없다.
- **VCT2 예산 축소:** 50k 검사는 이 속도에서 27초 안에 끝나지 않는다. 20k로 줄이면 절단 대신 예산 소진이 되어 재현성이 생긴다.
- **ponder:** 상대 차례에 예상 수의 V8-C/VCT2 결과를 미리 캐시한다.
- **solver 속도:** 1,600노드/초는 순수 Python 값이다. VCF를 C 확장으로 옮기면 §4.2의 표가 크게 바뀐다.
